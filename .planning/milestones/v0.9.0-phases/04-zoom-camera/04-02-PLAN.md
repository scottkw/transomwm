## Phase Goal

**As a** Mac user, **I want to** zoom out to see every window and zoom back in to any of them, **so that** I can find and focus any window fast.

<objective>
The engine half of the camera: a pure view planner, the two-step move protocol (`.cameraMove` out, `.cameraSettle` in), view-aware `planShown`, safe parks, the zoom-on collapse pass and the reveal timer. Zoom stays off by default, so Phase 3 is pinned by the existing suite.

Purpose: RESEARCH found every safety property the camera needs already in `planShown` (park once, save first, write only changes, echo suppression). Routing every camera write through it is the whole design (RESEARCH "Key insight").

Output: `ViewPlanner.swift`, `Arranger+Camera.swift`, `SettleTracker.swift`, Arranger inputs/effects, and three test files.

Design (Claude's discretion: camera internals, CONTEXT):
- `ViewTarget` is `.home` or `.node(NodeID)`; home is a case because the root ID changes on every split (RESEARCH Pattern 2). `.node(.desktop)` is the Desktop view.
- `LayoutTree.subtree(at:)` lives in TransomEngine (ViewPlanner.swift), not TransomModel: it uses only LayoutTree's public validating `init(root:nodes:states:)`, so no model change is needed (Ponytail). It throws on a missing node; the caller logs, never silently returns home.
- All camera state is one `CameraState` value (defined in Arranger+Camera.swift) stored as `var camera` in Arranger, so later plans add fields without touching Arranger's stored properties.
- The engine knows no animation: it emits start and end rects per tile and waits for `.cameraSettle`. Until 04-04 adds the stage, ArrangeController answers `.cameraMove` with an immediate `.cameraSettle`, so the protocol runs end to end from day one.
- Gap handles show only on displays at the home view (planner choice, flagged below).
</objective>
