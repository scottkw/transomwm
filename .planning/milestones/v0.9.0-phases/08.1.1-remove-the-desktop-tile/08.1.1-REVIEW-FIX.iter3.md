## Fixed Issues

### WR-01: The legacy home-frame rewrite applies the current World's home frame to every stored layout set where the window floats

**Files modified:** `Sources/TransomMac/LayoutStore.swift`, `Tests/TransomMacTests/LayoutStoreTests.swift`
**Commit:** 57431d4
**Status:** fixed: requires human verification (migration logic)
**Applied fix:** During the schema-3 (or older) migration, a home frame is now written only to the World it belongs to:
- If the window is anywhere in the current `world` (docked or floating), the home frame is applied there only, and only when the window is a shown floater.
- Otherwise the home frame is applied to the stored layout sets where the window is a shown floater.

A hidden floating tab member is skipped, as `bringBackParked` does, so it cannot move its whole group. New test `aHomeFrameFromTheCurrentWorldLeavesAStoredLayoutSetsFrameAlone` uses the V3 fixture with FileZilla (window 4) also floating in the layout set. It checks that the current World gets the home frame and the set keeps 100,100 500x400. The test failed before the fix and passes after it.

### WR-02: A floater lying over the dragged docked window's own tile can no longer be grouped with

**Files modified:** `Sources/TransomEngine/Arranger.swift`, `Tests/TransomEngineTests/ArrangerTabsTests.swift`
**Commit:** 169835c
**Status:** fixed: requires human verification (hover logic)
**Applied fix:** In the drag hover, `beneath` is now nil when the tile under the pointer is the dragged window's own leaf on its own desk. The own tile therefore never outranks a floater in `floatingGroupTarget`'s focus-recency check. New test `aDockedWindowDraggedOntoAFloaterOverItsOwnTileGroups`: `a` is docked, `t` floats over `a`'s tile, and `a` is focused after `t`. Dragging `a` onto `t`'s centre then gives the floating group `[t, a]`. The test failed before the fix and passes after it. The iteration-1 WR-03 test `aFloaterBehindAFocusedDockedWindowDoesNotGroup` still passes.
