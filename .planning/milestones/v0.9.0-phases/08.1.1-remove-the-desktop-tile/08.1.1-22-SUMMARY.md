# Phase 08.1.1 Plan 22: Empty areas behave as empty screen Summary

**An empty area left by a docking position now behaves as empty screen. Dragging a floating window over it shows nothing and only moves the window. Within 24 pt of the screen edge the drag previews exactly that empty area and docks into it. Dock Where It Is, New Windows: Tile, Arrange All and the Finder split (with no docked window focused) fill the largest empty area before they split any window. On an empty desk they still fill the screen (D-08). Focus, Move Window, Step In, Move View and the zoom band preview never land on an empty area. A gap handle beside one grows the window into it.**

## Accomplishments

- `DropTarget.fill(NodeID)` (8.1.1 D-16, E6). `DropZones.target` first looks up the leaf under the point, clamped into the root's rect. If that leaf is an empty area, it returns `.fill`, both inside and outside the 24 pt band. Otherwise the results are unchanged (`.layoutEdge` in the band, tile regions elsewhere). Both `applyDrop` overloads call `fill(id, with:, states:)`.
- `Arranger.hover` gives `.fill` the same edge-band filter as `.emptyLayout` (UI-SPEC discretion 2). `Planner.dockTarget` passes `.fill` through unchanged, so Dock Where It Is fills an empty area under the window's centre without any extra code.
- `largestTile` skips empty areas. The new `largestEmptyArea` uses the same ordering (by area, ties to the smaller NodeID) through one private `largest(_:where:)`.
- `autoTile` and `arrangeAll` fill the largest empty area first, then fall back to today's rules. `finderSplit` picks the focused docked tile, then the largest empty area, then the largest tile, then the layout edge. `FinderExpectation.target` is now a `DropTarget`, and `takeFinderWindow` applies it as is.
- E7: `Neighbours.neighbour` skips empty areas, which covers Focus, Move Window and the waiting-tile filter. `Navigator.stepIn` (both the pointer hit and the largest-child fallback) and `pan` skip them. `shownLeafRects` filters them out. Gap handles needed no code change, and a test now pins that behaviour.

## Notes for later plans

- When a docked window is dragged into the edge band of its own neighbouring empty area ([W | _]), the result is decide's snap-back miss. Removing W first empties the tree (E5), so the `.fill` target is stale and the dry run throws. Nothing breaks. If UAT wants W to move to the other half, that needs an E4-style vacate for `.fill` in `Arranger.dropping`.
- An explicit split beside a tile (a drag to a tile edge, or the Finder split with a focused tile) still shares weight across every sibling, empty areas included (today's `insert`). E2 covers only docking positions, so I left this alone.
