## Phase Goal

**As a** Mac user, **I want to** grant Pane access and have it track and move every window, **so that** no slow app or lock screen can freeze or lose them.

<objective>
Close verification gaps 4 and 5 (SAFE-05, WIN-02). One element that keeps failing must not switch `_AXUIElementGetWindow` off for the session, and successes must still count. A fallback ID must not stick for a window's life: synthetic and frame-matched IDs are re-checked and re-keyed through `WindowTracker.rekey(from:to:)` without a destroy and create pair, and no two elements ever share one ID. This is the project lead's decision of 2026-10-25.

Purpose: Since the WR-02 fix the cache is authoritative. A window identified during a brief lookup failure keeps a synthetic ID (so Phase 4 can never map it to an SCWindow) or a twin's real ID (so two elements share one ID). Cached elements no longer record successes, so one unplaceable element switches the lookup off process-wide after about 25 s (02-VERIFICATION gaps 4 and 5; REVIEW iteration 3 WR-03, WR-04).
Output: a WindowEvent.windowRekeyed event, WindowTracker.rekey, WindowIDResolver with per-element failure counting, the re-check and collision rules, a first-failure wait, and tests at the tracker, resolver and live levels.
</objective>

"Lead decision 2026-10-25" is the gap brief: one element that keeps failing must not switch `_AXUIElementGetWindow` off and successes must still be counted; re-check synthetic and frame-matched IDs, re-key through `WindowTracker.rekey(from:to:)` with no destroy and create pair, and never let two elements share one ID.

Facts that constrain the design (02-RESEARCH Pattern 4):
- `_AXUIElementGetWindow` succeeds for a hidden tab and returns -25201 for a closed window.
- Only a lookup failure on an element whose batched read succeeded with role AXWindow is an unexpected failure. Finder's desktop is not.
- `CapabilitySession` switches a capability off after 5 consecutive failures, and recordSuccess resets the count (Capabilities.swift lines 71-115).

Discretion choice (record it in the SUMMARY): successes are counted only from real lookups, meaning new elements and re-checks of fallback-identified elements. A cached `.axPrivate` element does not count as a success on later refreshes. Crediting cached elements would keep a lookup that really broke mid-session on forever, as long as any old window exists.

Event contract change (record it in the SUMMARY as a Phase 3 obligation): a new `WindowEvent.windowRekeyed(from: WindowRef, to: WindowInfo)`. LifecycleSync treats it as not applied today. Phase 3 must re-point any desk's WindowRef from `from` to `to.window`.

WindowIDResolver.swift (new, PaneMac, nonisolated, thread-confined) takes over Task 1's re-check and the existing `Fallback` struct.

State: `failed`, the elements whose lookup failure has already been counted. It is pruned on each resolve to the elements listed in that resolve.

resolve runs in two passes over the items.

Pass 1, for each item:
- A cached `.axPrivate` element keeps its ID with no lookup.
- Otherwise, while `lookup` is non-nil and the session still reports the capability available, call it once.
  - On success: record a success, drop the element from `failed`, and bind the returned ID. When a cached fallback ID differs, set replaces to it.
  - On failure of a readable AXWindow item: if the element is not in `failed`, record one failure and add it. Mark it first-failure when it was not in `failed` before.

Pass 2, for items still unbound:
- A cached element whose cached ID was not claimed in pass 1 keeps it.
- A cached element whose cached ID was claimed by another element in pass 1 is re-identified with the frame fallback excluding every bound ID, and replaces is set to its old ID.
- A new element gets the frame fallback, unchanged from today's Fallback (one CG snapshot on first need, names only for ambiguous matches, synthetic when ambiguous, nil without a CG list or frame). One exception: for a first-failure element, a match whose CG entry is offscreen is not accepted. That element stays nil and identityPending becomes true.
- Before inserting into byID, a key that is already taken leaves the later element unidentified this pass. This is defensive, and the invariant test proves it never fires in the covered cases.
