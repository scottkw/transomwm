## Summary

The diff reviewed is the 03-23 gap closure for G-03-8. It adds dormant saved windows at restore (`LayoutRestore.isAlive`, `reattach(_:tracked:live:)`), re-attaches them on the first `windowCreated` (`wakeDormant`), skips untracked windows in `planShown`, prunes them (`closeDormant` on inventory and on `appTerminated`), and wires `liveWindows` and `liveWindowsChanged` through `AXWindowSystem` and `ArrangeController`. The main hidden-Space path is correct and its tests are good. The rule "a layer-0 CG entry with the same windowID and pid means the saved window is alive", and the one-shot restore it plugs into, still have holes.

Every BLOCKER and WARNING marked "probe" below was reproduced headlessly against a copy of the tree at 8653fcc. The probe file is `/private/tmp/claude-501/-Users-ken-dev-panewm/fb58eaa5-8cd9-4b77-941d-64fed871017b/scratchpad/review0323/Tests/PaneEngineTests/ZZReviewProbeTests.swift`. It holds 5 probes that print their results, and it is not in the repo. The existing suites (ArrangerMultiDeskRestoreTests, ArrangerRestoreTests, LifecycleSyncTests: 45 tests) pass in that copy. Nothing was run that opens or moves windows, and nothing in the repo was modified.

Answers to the three questions asked:

1. **Verifier advisory (`liveWindows ?? []`): confirmed, and worse than "edge".** The probe shows that both a nil list and an empty list at the first complete inventory remove every hidden-Space window, and `snapshot` then hands the emptied desk to the next save. In the paused-at-launch case, `tracked` is also empty, so every saved window on every desk is removed. That part predates 03-23. A naive fix (defer the restore in the Arranger) would wedge the session, because ArrangeController feeds the "first complete inventory" only once. See CR-03.
2. **Docked Safari ghost (G-03-9):**
   - **In the running session, nothing changed.** CloseRule is untouched. The ghost stays tracked and present, so its tile stays reserved until Safari drops the CG entry, exactly as before 03-23. For a tracked window, the `planShown` filter change (`!= true` to `== false`) is a no-op.
   - **Across a relaunch, the tile is now reserved longer.** Before 03-23, `reattach` removed the untracked ghost at relaunch and the neighbours reflowed. Now `isAlive` keeps it dormant: it is layer 0 with the same pid, and the Space is not checked. The empty tile survives the relaunch, and layout.json keeps it across further relaunches. It ends only when Safari drops the entry (the next sweep emits `liveWindowsChanged`, then feed, then prune) or Safari quits. See WR-03. The same "alive but never tracked" rule also produces a worse, non-Safari case: CR-01.
3. **Dormant re-attach, prune ordering, persistence:**
   - **What works:** the prune ordering (`windows` replaced, then `closeDormant`, then `place`) and the `appTerminated` ordering (the event arrives before the tracker's `windowDestroyed`) are correct. Dormant state is persisted as ordinary desk entries plus the home frames that `isAlive` keeps, and it is pruned with `.save(.debounced)` and no undo step.
   - **What breaks:**
     - `wakeDormant` only runs when the window's first sight is a `windowCreated` event. An inventory fed first absorbs the window, and its real state is then never applied (WR-01).
     - `wakeDormant` does not release excluded windows (WR-02).
     - `wakeDormant` records a parked or stranded actual frame over the home frame that recovery put back (CR-02).

## Critical Issues

### CR-01: A docked native tab group whose shown tab is not its oldest member is duplicated at relaunch, and an empty tile is reserved on the shown desk (probe)

**File:** `Sources/PaneEngine/LayoutRestore.swift:21-22, 36-38`, with `Sources/PaneEngine/TabGroupTracker.swift:52-54`

**Issue:** A tab group's `WindowIdentity` is the identity of its oldest member "for the group's whole life" (TabGroupTracker.swift:52-54). A fresh tracker at relaunch founds the group under its first-seen visible member instead. So whenever the user left a non-leader tab selected (common with Finder, Terminal and TextEdit tabs), the saved identity (the leader) no longer matches the tracked one.

- **Before 03-23:** the saved entry was removed and the group came back floating. The layout was lost, but nothing else went wrong.
- **Now:** the leader is a hidden tab. It is still a layer-0 optionAll entry with the same pid, so `isAlive` keeps it dormant in its tile. Meanwhile the tracked group (under the shown tab's ID) is admitted as a new floating window.
- **Result:** the same physical window is both docked (an empty, reserved tile that `planShown` never writes) and floating. This happens on the Space that is shown, not just on hidden ones.
- **How long it lasts:** the dormant entry never wakes, because no `windowCreated` ever carries the leader's identity. It lasts until the leader tab closes or the app quits, and it persists in layout.json across relaunches.
- **Probe:** session 1 docks tab group [10, 11] and then selects tab 11 (tracked `10/vis11`). After the relaunch: tracked `11/vis11`, docked `[1, 10]`, floating `[11]`, `hasDormantWindows == true`.

**Fix:** Don't count a saved window as alive when the live CG entry belongs to a tracked tab group.

- **Smallest change:** restrict dormancy to the case G-03-8 actually is, a window on a known Space that is not shown. Carry each entry's SkyLight Spaces in `liveWindows`, and keep a saved window only if its Space set is non-empty and contains no shown Space. This also stops CR-01's hidden-tab twin on the shown Space and WR-03's Space-less Safari ghost. It does not fix a tab group on a hidden Space.
- **Complete fix:** have the window system report each tracked window's member IDs, and re-key a saved identity that matches a tracked group's member onto that group. The tile is then kept, not duplicated:

```swift
// WindowInfo: public var memberIDs: Set<UInt32>   (filled from TabGroupTracker)
// LayoutRestore.reattach, before the removal loop:
for info in tracked where info.idSource != .synthetic {
    for saved in savedWindows where saved.pid == info.window.pid && info.memberIDs.contains(saved.windowID) && saved != info.window {
        try world.rekey(from: saved, to: info.window, history: &history)
    }
}
```

Add a regression test: dock a two-tab group, select the non-leader tab, relaunch on a fresh fake. Expect one entry, docked, and no dormant windows.

### CR-02: Recovery launch strands a parked floating window from a hidden Space offscreen, because `wakeDormant` overwrites the home frame that recovery put back (probe)

**File:** `Sources/PaneEngine/Arranger.swift:557-560` (wakeDormant), with `:212-215` (showParkedDesktops) and `:372-387` (rescueStranded, tracked windows only)

**Issue:** Session 1 has a floating window 3 on a Space 2 desk whose Desktop tile is hidden, so 3 is parked at `1439,899`. Pane crashes on Space 1.

1. During the recovery restore, `showParkedDesktops` shows that desk's Desktop and writes 3's home frame (`730,400`) into the desk. The home frame is then spent (Arranger.swift:171-174). `rescueStranded` skips 3, because it is not tracked.
2. When Space 2 is shown, `wakeDormant` calls `world.recordFloatingFrame(info.frame)` with the parked frame. This replaces the frame the desk was about to move the window back to.
3. `planShown` then sees the actual frame equal to the desk frame, and sends nothing.

The window stays at `1439,899` (`Recovery.isStranded == true`) for good. That breaks D-17 / SAFE-03 ("stranded windows come on screen") for hidden-Space windows. The plan claimed the recovery launch is covered because it runs the same re-attach.

The probe also ran a normal launch. There the Desktop stays hidden, the home frame survives, and Show Desktop brings the window back to `730,400`, so the normal launch is fine. Before 03-23 the outcome was also stranded (the window was dropped, then re-admitted at its parked frame), so this is not a regression in outcome. It is the new code path that defeats the rescue it was given.

**Fix:** Don't record an actual frame that is parked or stranded over the desk's frame. Let `planShown` move the window back:

```swift
} else if info.state == .present, world[key]?.tree.isDesktopHidden != true,
          !Recovery.isStranded(info.frame, displays: displays) {
    try world.recordFloatingFrame(info.frame, for: info.window)
}
```

Also make sure `lastRequested` is not seeded for that window, so the desk frame is written. Add a recovery-mode test with a parked dormant floater.

### CR-03: A nil or empty `liveWindows` at the first complete inventory removes every hidden-Space window, and that is saved (the verifier's advisory, confirmed) (probe)

**File:** `Sources/PaneEngine/Arranger.swift:200-210`, `Sources/PaneEngine/LayoutRestore.swift:14`, `Sources/PaneMac/AXWindowSystem.swift:131-132, 152, 297`, `Sources/PaneMac/ArrangeController.swift:130-136`

**Issue:** The prune path (line 196) treats nil, empty and paused lists as "decide nothing". The restore path collapses nil to `[]` (line 205) and never checks for empty. The restore runs exactly once.

- **Probe:** with `liveWindows = nil` and with `liveWindows = []`, the Space 2 desk ends `docked []`, and `snapshot.world` (what layout.json gets) holds the emptied desk.
- **Live triggers:**
  - `CGWindowList.snapshot()` fails during the initial sweep.
  - Pane starts while the session is paused (locked or asleep). In that case `start()` still sets `initialRefreshComplete = true` after a sweep that refreshed nothing (`refresh` returns early while `paused`). The inventory has `sessionPaused: true`, `liveWindows: nil` and `windows: []`. `reattach` then removes every saved window on every desk, the shown one included. That part predates 03-23, but it is the same unguarded restore.
- **Threat model:** T-03-63 says "a hidden desk is never wiped by a blank list", which is not true for the restore path.
- **Fix trap:** a guard in the Arranger alone (returning `[]` and keeping `pendingRestore`) would wedge Pane. `ArrangeController` feeds the first complete inventory only once (`fedCompleteInventory`), and `.event` inputs are dropped while `pendingRestore != nil` (Arranger.swift:229).

**Fix:** Make the restore wait for a usable list, and make the shell feed again until it has happened:

```swift
// Arranger, restore branch
guard inventory.initialRefreshComplete, !inventory.sessionPaused, let live = inventory.liveWindows, !live.isEmpty else { return [] }
// public var awaitsRestore: Bool { pendingRestore != nil }

// ArrangeController events loop
var feed = (self.arranger.awaitsRestore || !self.fedCompleteInventory) && inventory.initialRefreshComplete
```

Also drop the `live: [CGWindowEntry] = []` default from `LayoutRestore.reattach`. A future caller should not silently get the pre-03-23 drop behaviour. Add tests that feed a restore inventory that is locked, nil-list or empty-list: nothing removed, and the restore still pending, then completed by the next good inventory.

## Warnings

### WR-01: An inventory that absorbs a dormant window before its `windowCreated` skips `wakeDormant`, so the desk keeps the saved state (probe)

**File:** `Sources/PaneEngine/Arranger.swift:193, 481-485`; `Sources/PaneMac/ArrangeController.swift:126-135`

**Issue:** `wakeDormant` runs only when `windows[id] == nil` at the window's `windowCreated`. `ArrangeController` reads `system.inventory()` after each event. Both actors live on main, so the inventory can already include windows whose `windowCreated` is still buffered in the stream. 03-23 makes those feeds frequent: every `liveWindowsChanged` while any window is dormant.

When the race hits, `.inventory` sets `windows[id]` and `place` only rehomes and admits. The later `windowCreated` sees `windows[id] != nil`, so the real state is never applied. `lastRequested` is not seeded, and a floating window's frame is not recorded.

Probe: dormant 3 is saved `.present` but is minimized in the fresh fake. In the raced run, the tracker says `.absent` and the desk stays `.present` (the control run shows `.absent`). The planner then keeps a tile for, and writes to, a window that is not there, until some later state event happens to correct it.

**Fix:** In the `.inventory` branch, before replacing `windows`, remember which identities were dormant, then wake those the inventory now tracks:

```swift
let wasDormant = Set(dormantWindows.map(\.identity))
windows = Dictionary(...)
for info in inventory.windows where wasDormant.contains(info.window.identity) {
    do throws(LayoutError) { try wakeDormant(info) } catch { faults.append(.fault("...")) }
}
```

### WR-02: A dormant window whose app was excluded while it was dormant stays docked when it wakes (D-29) (probe)

**File:** `Sources/PaneEngine/Arranger.swift:554-563, 481-486, 539`

**Issue:** `tracker.setExcluded` emits `windowChanged` (and so `release`) only for tracked windows. A dormant window of a newly excluded app stays docked. When it wakes, the `windowCreated` path runs `wakeDormant` and then `admit`, which returns early for excluded windows and windows already on a desk. Nothing calls `release(info)`. Only `windowChanged` and `place` do that.

Probe: window 3 of app 901 docked on Space 2, dormant, app 901 excluded, Space 2 shown. Result: `excluded = true`, docked `[4, 3]`.

So the excluded window keeps a docked tile that `planShown` never writes (the `isExcluded == false` filter). Its neighbours don't take that room. The user can drag the excluded window over docked neighbours, and it is never corrected (`moved` returns early for excluded windows). That is an overlap the Core Value rules out. Before 03-23, the window was dropped at restore and `admit` refused it.

**Fix:** In `wakeDormant`, call `try release(info)` after applying the state and before `rehome(info)`.

### WR-03: A docked window that a G-03-9 ghost keeps alive now holds its empty tile across relaunches, and so does any other "alive but never AX-listed" window

**File:** `Sources/PaneEngine/LayoutRestore.swift:36-38`; `Sources/PaneMac/AXWindowSystem.swift:297`

**Issue:** `isAlive` accepts any layer-0 optionAll entry with the same ID and pid. Safari keeps a closed window's entry at layer 0, offscreen, with an empty Space set (g-03-9 evidence 02:41).

- **Running session:** unchanged from before 03-23 (see Summary item 2).
- **After a relaunch:** the ghost is now kept dormant in its tile. Before 03-23 it was removed, and the neighbours reflowed.

The same applies to T-03-65 windows on the shown desk (an app whose first AX read failed). Their tiles are reserved and nothing is written to them. This is bounded by Safari releasing the entry (pruned within one 5 s sweep after that), but it is persisted to layout.json across further relaunches. The verifier's human item 5 should be extended: dock Safari, Cmd-W, relaunch Pane within the ghost's lifetime, and check whether the tile is still reserved after the relaunch.

**Fix:** This belongs with the Phase 6 G-03-9 fix, but the restore side is cheap now. Have `AXWindowSystem` drop entries whose SkyLight Space set is known and empty from `liveWindows` (`SkyLightSpaces.spaces(of:)` is already called per refresh). Or adopt CR-01's "known Space, not shown" rule. Before excluding Space-less entries, check what Spaces minimized windows and hidden tabs report (g-03-9 blind spots).

### WR-04: `liveWindowsChanged` feeds the whole inventory, whose `place()` rehomes the window being dragged and resets its drag-poll frame. It now fires on every layer-0 CG change while any window is dormant

**File:** `Sources/PaneMac/ArrangeController.swift:132`; `Sources/PaneEngine/Arranger.swift:193, 320-326`

**Issue:** The prune is driven by a full `.inventory`, which:
- replaces `windows` wholesale, overwriting the `.dragFrame` 60 Hz frame (Arranger.swift:284);
- runs `place()`, whose loop calls `rehome(info)` with no `drag?.window != info.window` guard. The `windowChanged` path has that guard (line 536) precisely because "where it lands is decided at mouse-up".

Before 03-23 this happened only on `displaysChanged`. Now it happens on any layer-0 window appearing or disappearing for any tracked app (Safari's never-listed layer-0 strips 1332-1335 are such windows), for as long as `hasDormantWindows` holds. That can be a whole session: a Space the user never revisits, CR-01's tab-leader ghost, WR-03's Safari ghost. A window dragged across displays can be rehomed mid-drag.

**Fix:** Either give pruning its own input that touches nothing else:

```swift
case .liveWindows([CGWindowEntry])   // Arranger: guard !sessionPaused, !live.isEmpty; return closeDormant { !isAlive } + (changed ? replan() : [])
```

and have ArrangeController send `.liveWindows(inventory.liveWindows)` on `.liveWindowsChanged`. Or, at minimum, skip `rehome` in `place()` for `drag?.window`.
