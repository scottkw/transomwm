## Phase Goal

**As a** Mac user, **I want to** drag windows into nested tiles that reflow as windows open and close, **so that** my windows never overlap.

<objective>
Close G-03-11 (floaters stay shrunk, and some end below the screen, after a gap drag shrinks and grows the Desktop) and the reopened G-03-4 (the green button on a desk's only docked window has no visible effect). Both are fixed by one design: a per-window wanted frame that only user actions write, plus a floor that stops a boundary drag at a floater's real size. This plan does the in-session engine half. 03-26 saves the wanted frames in layout.json.

Root causes (binding, from 03-UAT.md and the two debug sessions):
- G-03-11 A. A floater has one stored frame (`FloatingWindow.frame`). `Arranger.moved` records every frame event into it, including the echo of Pane's own clamp (Arranger.swift:639, before the own-write check at 642). Each gap-drag step's clamp therefore replaces the frame the user gave the window. When the Desktop grows back, the small stored frame overlaps no tile, so no plan enlarges it.
- G-03-11 B. During a live drag, the Desktop tile's minimum (Planner.swift:30) does not know the floaters' real heights. The drag shrinks the Desktop below them, the apps refuse, and the windows hang below the Desktop and the screen. The learner needs a repeat write at least 1 s later, which A prevents.
- Chesterton fence (debug E1): line 639 is load-bearing. The recorded frame is also where the window really is. Dock's centre (772), the Planner's overlap test (Planner.swift:55) and planShown (1451) read it, and dropping the echo record breaks TooBigDockedWindowTests. So the fix adds a separate record, the wanted frame, and leaves `FloatingWindow.frame` as the fact it is today.
- G-03-4 reopened. Pane takes the click and toggles. But on a desk whose only docked window is the clicked one, `float` keeps the tile rect (the Desktop becomes the whole area, so the clamp does nothing), and `dock` puts it back in the same tile. Nothing moves. User decision 2026-10-27: Float returns the window to its pre-dock frame, clamped into the Desktop. Without a known pre-dock frame it gets a slightly smaller centred frame. Docking fills the tile.

Design (smallest complete change):
1. `Arranger.wantedFrames: [WindowIdentity: Rect]`. The writers are listed in must_haves. Undo does not touch it: like home frames, it is per-window intent, not a desk edit. An undo that floats a window again shows it at its kept wanted frame, which is the pre-dock frame.
2. `Planner.plan` gains `wanted:`. For each present floater, `want` is its wanted frame, or its recorded frame when it has none. The target is `clamp(want, into: Desktop)` when `want` overlaps a docked tile, otherwise `want` itself. The floater is planned when its recorded frame overlaps a tile, or is more than 0.5 pt off the target. With no wanted frames this is exactly today's rule, so every call site that passes none behaves as at HEAD. Only `planFloatingLostRoom` passes `wantedFrames`. That function feeds planShown and each live gap-drag replan.
3. Orchestrator default narrowed (evidence below). The orchestrator wanted every floater that sticks out past the Desktop clamped back in. Applied to all floaters, that broke 7 existing tests, including the 03-04 fence `aFloatingWindowOffTheScreenEdgeButClearOfTilesIsLeftAlone`. So a floater the user leaves past the screen edge, clear of tiles, is still left alone (D-24). A floater that Pane's own clamp left sticking out is corrected, because its recorded frame is off its target, and B stops the drag before that can happen.
4. B: `floaterFloors`. When a floating window's read-back is larger than the request on an axis by more than `MinimumSizeLearner.tolerance`, that axis's floor is set at once. Only `boundaryChange` uses floors, merged into the sizing of the floaters on the Desktop. So a gap drag or a docked edge resize is cut at the floater's real size. Dock fit tests and planShown never see floors: counting them there failed TooBigDockedWindowTests in the experiment. Floors are session-only and never feed the learner or the hints.
5. G-03-4: `Planner.floatFrame(wanted:tile:desktop:minimum:)`. It returns `clamp(wanted, into: desktop)` unless there is no wanted frame or the clamp is within 2 pt of the tile. Otherwise it returns a frame centred in the Desktop, sized to 90% of the tile per axis, at least the known minimum, and at most the Desktop. `float()` uses it and records the result as the window's wanted frame. Float All (TILE-16) keeps its tile-rect placement. The decision names Float and the green button only.

Out of scope here: persistence of wanted frames (03-26), the VM re-check (the orchestrator runs it in the Tart VM afterwards), and any undo redesign.
