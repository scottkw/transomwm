## Summary

This diff covers three plans:

- **03-24 (G-03-10):** a sweep counts as the initial one only if no pause happens from its start to its end. A pause counter in `AXWindowSystem` tracks this, and the fake mirrors the rule.
- **03-25 (G-03-11, G-03-4):** adds per-window wanted frames and floater floors. Float now goes to the pre-dock frame, or to a centred frame 90% of the tile's size.
- **03-26:** saves wanted frames in layout.json as an optional, validated key.

The main paths are correct and well tested: the gap drag that shrinks the Desktop and grows it back, the late clamp, the locked start, the relaunch round trip and the moved-while-off rule.

The real defect is in the own-write detection that 03-25 now depends on. A floater's last read-back (`lastApplied`) is never consumed. When a later move brings the window back within 2 pt of that read-back, Pane classifies the move as its own, keeps the stale wanted frame, and the next re-plan moves the window away again. Before 03-25 the same misclassification only skipped a clamp, so it did no harm. Now Pane fights the user (CR-01).

Two further warnings are about wanted frames being lost: Float overwrites the pre-dock frame with its clamp (WR-01), and Float All followed by Undo loses every pre-dock frame (WR-02).

Each BLOCKER and WARNING marked "probe" was reproduced headlessly against a copy of the tree at 7c02466. The probe file is `/private/tmp/claude-501/-Users-ken-dev-panewm/fb58eaa5-8cd9-4b77-941d-64fed871017b/scratchpad/review0326/Tests/PaneEngineTests/ZZReviewProbe0326Tests.swift`. It is not in the repo. Every probe was headless: PANE_LIVE was never set, neither Pane nor PaneFixtureApp was launched, and the VM was not used.

Answers to the focus questions:

1. **Wanted-frame writers.** The list in the 03-25 SUMMARY matches the code: admit, release, rehome, the user's floater moves, missed, commitUndock, Snap, Float, Float All, lost-room floats, wakeDormant, the reattach seeding and rescueStranded's stranded-only replacement. Undo, parks and Pane's echoes leave wanted frames alone. Two writers break the rule "Pane's clamps never write it":
   - Float stores its clamp of the pre-dock frame (WR-01).
   - Float All stores tile rects (WR-02). This is a documented decision, but combined with Undo it destroys the pre-dock frames.
2. **Floater floors during boundary drags.** Correct for the cases tested. A floor is only set from a refused read-back of a floating window, and it drops on any frame event below it. Floors are passed only to `boundaryChange`. A floor is not cleared when the window docks, and an axis that drops leaves a `0` entry behind (IN-05). That is minor.
3. **Own-write detection.** The `lastRequested` half is safe, because `planShown` prunes it as soon as the floater is no longer planned. The `lastApplied` half is never pruned for a floater, which causes CR-01. The "any floater frame while a boundary drag is live" rule depends on `liveGap` being cleared, and nothing clears it except a delivered mouse-up (IN-03).
4. **Float and Dock frame choice.** `Planner.floatFrame` is right as specified. A pre-dock frame only 2 pt from the tile still counts as "moved", so the toggle can move a window by only a few points (IN-04).
5. **layout.json.** Decoding, validation and backward compatibility are sound:
   - `decodeIfPresent` handles a file with no `wantedFrames` key.
   - Duplicate and out-of-range wanted frames are rejected.
   - An older Pane ignores the key.
   - `snapshot` returns the saved wanted frames while a restore is pending or unattached.

   One gap is shared with home frames: a 0x0 frame passes both validation and the stranded check (IN-01).
6. **AXWindowSystem pause counter.** No defect found. `AXWindowSystem` is `@MainActor`, so `pauseCount` and `initialRefreshComplete` are only touched between suspension points. A lock and unlock during the sweep's `await withTaskGroup` bumps `pauseCount`, so that sweep does not count. The completing sweep is always followed by `.sessionPaused(false)` from `resumeTask`, or by the next event, so ArrangeController's `feed` still fires. Two concurrent sweeps can both run `initial: true`. That is harmless, because `inFlight` collapses per-pid jobs. This half has no headless coverage (IN-06).
7. **Undo interplay.** Undo leaves wanted frames alone, as designed. Because wanted frames are not in the snapshots, an undone command that overwrote them cannot give them back (WR-02). A floater the user moved after the snapshot keeps its current frame after Undo. Probe E confirmed this, so there is no stale recorded frame.
8. **Memory growth.** None found:
   - `forget` clears `wantedFrames` and `floaterFloors`, and so covers `windowDestroyed`, a `.closed` state and `closeDormant`.
   - `windowRekeyed` moves both.
   - `reattach` keeps only the saved wanted frames whose windows the re-attached World holds.
   - Every other writer writes only for windows that a desk holds.

## Critical Issues

### CR-01: A floater moved back onto Pane's last write is treated as Pane's own, and the next re-plan moves it away again (probe)

**File:** `Sources/PaneEngine/Arranger.swift:688-690, 700`, with `:546` (`lastApplied` is only cleared in `forget`)

**Issue:**

- **How a move counts as Pane's own.** `moved` treats a floater's frame as Pane's own when it is within 2 pt of `lastApplied`. `lastApplied` is the read-back of Pane's last write to that window. Nothing clears it until the window closes. An own move does not update `wantedFrames` (line 690). Since 03-25 the Planner moves any floater whose recorded frame is more than 0.5 pt from its wanted frame (`Planner.swift:65-69`).
- **What goes wrong.** Any later move that brings the window back to where Pane last put it is swallowed: the frame is recorded, but the wanted frame keeps the previous position, and the next re-plan writes it back.
- **Why this matters now.** Before 03-25 this case only skipped a clamp, so it was harmless.
- **How to trigger it.** It needs a move that does not go through a Pane drag session, because `missed()` writes the wanted frame unconditionally. Examples:
  - double-clicking the title bar to zoom and then zoom back, which is the macOS default;
  - Window > Center, which matches the centred 90% fallback when the desk has nothing else docked;
  - a keyboard window manager;
  - AppleScript;
  - an app restoring its own frame.
- **Probe A** (`Harness.started(frames: [1: frame1])`):
  1. Dock w1, then press the green button. w1 floats to `frame1`, and `lastApplied = frame1`.
  2. The user zooms it to (0,25 1440x875). This is not own, so the wanted frame becomes the zoomed frame.
  3. The user un-zooms back to `frame1`. This counts as own, so the wanted frame stays the zoomed frame.
  4. Any event (here `windowFocused`) then gives `setFrame(w1, 0,25 1440x875)`. Pane re-zooms the window the user just un-zoomed.

This breaks D-23/TILE-07: a floater the user moves is never moved back.

**Fix:** A read-back stops being "the frame Pane just wrote" once the window has been anywhere else. Clear it on the first move that is not Pane's own. Optionally, also clear it once its echo has been consumed:

```swift
let own = ...
if floating, !own {
    wantedFrames[window.identity] = frame
    lastApplied[window.identity] = nil   // the user (or app) moved it: Pane's last read-back is history
}
```

`aClampTheAppAppliesLateIsStillPanesOwn` is unaffected, because its late frame counts as own through `liveGap`. Add probe A as a regression test, plus a Window > Center variant: no pre-dock frame, so the window floats to the centred frame, the user moves it, then centres it again.

## Warnings

### WR-01: Float stores its clamp of the pre-dock frame as the new wanted frame, so the pre-dock frame is lost once the Desktop grows back (probe)

**File:** `Sources/PaneEngine/Arranger.swift:868-877` (`wantedFrames[window.identity] = world[key]?.desktop.frame(of: window)`)

**Issue:**

- **The design rule.** 03-25's rule is that Pane's clamps never overwrite a wanted frame. That way a floater goes back to its frame when the Desktop grows again, which is the G-03-11 premise.
- **What Float does.** Float clamps the pre-dock frame W into the Desktop that the undock leaves, then records the clamp as the wanted frame.
- **Probe C.** w1's pre-dock frame is (100,100 1200x700), and w1 and w2 are both docked.
  1. Float w1. It lands at the clamp (100,466 1200x426), and the wanted frame becomes that clamp.
  2. Float w2. The Desktop is now the whole screen, but w1 stays at 1200x426.

  If W had been kept as the wanted frame, the Planner would have placed w1 at `clamp(W)` while w2 was docked, and at W afterwards. This is the same behaviour as a gap drag.

**Fix:** When Float used W (not the 90% fallback), keep W as the wanted frame. The Planner already plans `clamp(W)` while W overlaps a tile.

```swift
let placed = Planner.floatFrame(wanted: wanted, tile: tile, desktop: desktop, minimum: mins[window])
...
let usedWanted = wanted.map { !Planner.near(Planner.clamp($0, into: desktop), tile, within: 2) } ?? false
wantedFrames[window.identity] = usedWanted ? wanted : world[key]?.desktop.frame(of: window)
```

`desktop` is computed inside the edit closure, so the decision has to come out of the closure, or the clamp has to be recomputed after it. Add a test: two docked windows, float the one with the large pre-dock frame, float the other, and expect the first back at W.

### WR-02: Float All, and any undock that is later undone, permanently replaces the pre-dock frames; Undo cannot bring them back (probe)

**File:** `Sources/PaneEngine/Arranger+Commands.swift:143`, `Sources/PaneEngine/Arranger.swift:877, 1296`, with the Undo doc at `Arranger.swift:881-884`

**Issue:**

- **What gets overwritten.** Float All writes each docked window's clamped tile rect as its wanted frame, and commitUndock and Float write their landing frames.
- **Why Undo cannot help.** Wanted frames are not in the undo snapshots. Undoing one of these commands re-docks the windows, but their pre-dock frames are gone.
- **Probe B.**
  1. Dock w1, whose pre-dock frame is `frame1`.
  2. Float All, then Undo. w1 is docked again, and its wanted frame is (8,33 708x859), its old tile.
  3. Float w1. `floatFrame` sees a wanted frame on the tile, falls back, and gives (401.4,75.95 637.2x773.1) instead of `frame1`.

A mis-pressed Float All followed by Undo silently breaks G-03-4's "Float goes back to the pre-dock frame" for every window on the desk.

**Fix (pick one):**

- **(a)** Have Float All and commitUndock keep a prior wanted frame. Write their landing frame only when the window has none, and let the Planner clamp it. This keeps TILE-16's tile-rect landing, because Float All can still add the window at the tile rect while the wanted frame keeps W.
- **(b)** Store wanted frames per desk in the undo snapshot. That costs more, because it changes the snapshot type.

Option (a) is the smaller change. Add probe B as a test.

## Info

### IN-01: A 0x0 wanted frame passes validation and the stranded check, so Pane would send a 0x0 setFrame

**File:** `Sources/PaneMac/LayoutStore.swift:110-113`, `Sources/PaneModel/Geometry.swift:59-61` (`width >= 0 && height >= 0`), `Sources/PaneEngine/Recovery.swift:32` (`guard frame.width > 0, frame.height > 0 else { return false }`)

**Issue:** A wanted frame with zero width or height in an edited or corrupt layout.json is accepted. `reattach` keeps it, because a zero-area frame is "not stranded". The Planner then writes it for a floater, and Float uses it for a docked window: `clamp` keeps 0x0, which is not near the tile. Home frames have the same hole, so this is not new with 03-26, but T-03-73 says the validation is the mitigation.

**Fix:** In `LayoutStore.decode`, also require `wanted.frame.width > 0 && wanted.frame.height > 0`, or drop such frames in `reattach`'s `wanted` filter.

### IN-02: `restore(..., wantedFrames: = [:])` and `LayoutFile.init(..., wantedFrames: = [:])` defaults let a caller drop wanted frames silently

**File:** `Sources/PaneEngine/Arranger.swift:12`, `Sources/PaneEngine/LayoutFile.swift:44-46`

**Issue:** Each has one production caller (`ArrangeController.swift:113, 488`), and both pass the value. A future call site that leaves the argument out compiles and loses every pre-dock frame on the next save. The defaults exist only for older tests.

**Fix:** Remove the defaults and pass `[:]` explicitly in the tests. The project's CLAUDE.md principle says the same: a silent fallback hides a hard failure.

### IN-03: The rule "a floater's frame during a boundary drag is Pane's own" depends on `liveGap` being cleared, and only a delivered mouse-up clears it

**File:** `Sources/PaneEngine/Arranger.swift:689`, with `:149`, `:1571`, and `Sources/PaneMac/Overlay/GapHandlePanels.swift:151-167`

**Issue:**

- **What clears `liveGap`.** Only `gapDrag(ended: true)` and a failed live re-plan clear it.
- **How a mouse-up can be lost.** `hideHandles()` runs on pause and on a Space change, and it orders the handle panel out, possibly mid-drag. A mouse-up after that may never reach the `HandleView`.
- **The effect.** If `liveGap` is left set, every later frame event of every floater counts as Pane's own, so no keyboard or app move updates a wanted frame, and every re-plan keeps applying the stale live delta.
- **Scope.** This is not reproduced; it depends on AppKit's mouse-up delivery to an ordered-out panel. 03-25 makes the outcome worse.

**Fix:** Clear `liveGap` in `setPaused(on)`, on `.sessionPaused(true)`, on `spaceChanged`, and at the start of any `pointer(.down)`.

### IN-04: Float's "back on the tile" test is 2 pt, so a pre-dock frame a few points off the tile still makes the toggle look like it did nothing

**File:** `Sources/PaneEngine/Planner.swift:82-90`

**Issue:** G-03-4's complaint was that the toggle does not visibly move the window. A pre-dock frame 3 to 10 pt from the tile is clamped and returned as is. One example is a window the user had filled to the visible frame, on a desk whose gap is 8 pt: the tile is inset 8 pt from the edges. The window then moves only a few points.

**Fix:** Fall back to the centred frame when the clamped frame overlaps the tile by more than about 90% of the tile's area, or is within `max(2, gap)` per edge.

### IN-05: Floater floors outlive docking, and an axis that drops leaves a zero entry

**File:** `Sources/PaneEngine/Arranger.swift:112, 549-555, 692-697`, `Sources/PaneEngine/Planner.swift:30-34`

**Issue:**

- Docking does not clear `floaterFloors`, so a floor learned while the window floated applies again after a later Float. The floor is still something the app once refused, so this is a mild staleness.
- A floor whose axes both drop to 0 stays in the dictionary as `Size(0, 0)`. `Planner.plan` then adds a zero-size entry to `sizing`.
- The 2 pt tolerance also lets an app that rounds its size up (size increments, aspect ratio) set a floor that is not a real minimum. That would make a later gap drag stop early. This is speculative and not probed.

**Fix:** Drop the entry when both axes are 0. Optionally clear it in `dock`, `commitDock` and `arrangeAll` for the windows that dock.

### IN-06: The AXWindowSystem pause-counter rule has no headless test, and the fake cannot express "a pause began during the sweep"

**File:** `Sources/PaneMac/AXWindowSystem.swift:289-320, 550-551`, `Sources/PaneTestSupport/FakeWindowSystem.swift:389-393`

**Issue:** The fake's `refreshAll` is synchronous and only checks `locked && lockGate` at its end. The plan-check W1 case (a lock and unlock inside one sweep leaves it uncounted) is therefore untested anywhere, and the 03-24 SUMMARY records it as a coverage gap.

The code is correct by inspection:

- the class is MainActor-isolated;
- `pauseCount` is bumped before every other step of `sessionDidPause`;
- `.sessionPaused(false)` always follows the completing sweep.

**Fix:** Optional. Add a fake hook that toggles the lock between two apps' refreshes inside `refreshAll`, and a test that the inventory stays `initialRefreshComplete == false` until the next unpaused `refreshAll`.
