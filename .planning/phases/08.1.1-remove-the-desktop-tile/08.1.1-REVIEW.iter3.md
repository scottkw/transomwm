## Warnings

### WR-01: The legacy home-frame rewrite applies the current World's home frame to every stored layout set where the window floats (introduced by the WR-01 fix)

**File:** `Sources/TransomMac/LayoutStore.swift:173-187`

**Issue:** `homeFrames` is one global map. `LayoutSet` stores only `arrangement`, `world` and `lastUsed` (`Arrangements.swift:34-44`), and a home frame is in the coordinates of whichever World parked the window. The fix writes `home.frame` as the floating frame:
- in `contents.world`, if the window floats there, and
- in **every** `contents.layoutSets[i].world` where the window floats.

The same window usually exists in several arrangements, because sets are snapshots of the same windows under other display configurations. Two cases go wrong:
- **Window W floats in both the current World and set B.** In the current World W was parked by a hidden Desktop, with home frame H_A in arrangement A's coordinates. In B, W is floating at its real frame F_B. After migration, B's stored frame for W is H_A, which may sit on a display that B does not have.
- **Window W is docked in the current World and camera-parked there.** Its home frame is its tile rect. If W floats in some set B, B's floater gets the current World's tile rect.

When B is applied (`Arranger.swift:567-570`, `reattach(merged, …)`), `reattach` overwrites the stored frame only for tracked **present** floaters (`Arranger.swift:772-775`). A minimized, hidden-Space or not-yet-answered window keeps H_A. When it later shows, the "floating window not where the model has it" pass (`Arranger.swift:2197-2206`) moves it to H_A. That pass has no stranded check, so the window can go off screen. In either case the user's B position F_B is lost.

The fixture test does not cover this case: the set holds only window 5, which has no home frame (`LayoutStoreTests.swift:495-498`).

There is also a smaller point. For a floating tab group, `DesktopLayer.setFrame` on any member moves the whole group (`DesktopLayer.swift:72-79`). The loop runs in identity order, so the last member with a home frame decides the group frame. `bringBackParked` skips hidden tabs (`!isHiddenTab`). The migration should do the same.

**Fix:** Apply each home frame only to the World it belongs to. Because of the old sweep, an entry for a window that is anywhere in the current World (docked or floating) belongs to the current World. Only an entry for a window absent from the current World can belong to a set:
```swift
if version < LayoutFile.schemaVersion {
    for (index, home) in contents.homeFrames.enumerated() {
        let window = WindowRef(identity: home.window)
        func isShownFloater(_ world: World) -> Bool {
            world.desks.values.contains { desk in
                desk.desktop.contains(window)
                    && desk.desktop.group(containing: window).map { $0.members[$0.selected] == window } ?? true
            }
        }
        do throws(LayoutError) {
            if contents.world.desks.values.contains(where: { $0.contains(window) }) {
                if isShownFloater(contents.world) { try contents.world.recordFloatingFrame(home.frame, for: window) }
            } else {
                for i in contents.layoutSets.indices where isShownFloater(contents.layoutSets[i].world) {
                    try contents.layoutSets[i].world.recordFloatingFrame(home.frame, for: window)
                }
            }
        } catch { throw .invalidEntry("home frame \(index): \(error)") }
    }
}
```
Add a test: W floats in `world` (parked, with a home frame) and also floats in a layout set at F_B. After load, the set still has W at F_B.

### WR-02: A floater lying over the dragged docked window's own tile can no longer be grouped with (introduced by the WR-03 fix)

**File:** `Sources/TransomEngine/Arranger.swift:1750-1751`, `Sources/TransomEngine/Arranger+Tabs.swift:255-260`

**Issue:** `beneath` comes from `target` before the own-tile exclusion. That exclusion runs later, in the `switch` at `Arranger.swift:1757`. `dragPlan` plans the desk with the dragged window still in its tile (`Arranger.swift:2078`). So when a docked window W is dragged and the pointer is over W's old tile, `beneath` is W's own leaf, and `docked` is W itself, or the selected member of W's group, which is W when W is the one being dragged. Pressing W's title bar focuses W, so `focusOrder[0] == W`, `recency(W) == 0`, and `recency(docked) < recency(top.window)` is always true. `floatingGroupTarget` returns nil.

Here is the case that breaks. Floater F overlaps part of docked W's tile (allowed under D-05). The user drags W away; F is now plainly visible where W was. The user drops on F's centre. Before 35042a3, F took the group. Now the hover falls through to the own-tile case, `target = nil`, and the release is a snap-back miss. The new test (`ArrangerTabsTests.swift:750-768`) drags a floater over another window's tile, so it does not exercise this case.

**Fix:** Ignore the dragged window's own leaf as a competitor, since it is not in front of anything while it is being dragged:
```swift
// Arranger.swift, hover
let ownLeaf = ownDesk.tree.leaf(containing: window)
let beneath: NodeID? = if case .tile(let id, _)? = target, !(key == ownKey && id == ownLeaf) { id } else { nil }
```
Alternatively, in `floatingGroupTarget`, skip the check when `docked == dragged` or when `beneath == desk.tree.leaf(containing: dragged)`. Add a test: F floats over docked a's tile, a is focused, a is dragged onto F's centre, and a groups with F.

### IN-06: Arrange All's new "nothing placed" branch is not covered by the per-window skip

**File:** `Sources/TransomEngine/Arranger+Commands.swift:151-161`

**Issue:** The `largestTile` branch catches an `insertLeaf` failure and counts that window as skipped ("a full split"). The new `else` branch calls `trial.tree.applyDrop(.layoutEdge(.right), …)` without a catch. If the root is a same-axis split already at `LayoutTree.maxChildren`, or the tree is at `maxNodes`, and none of its leaves is placed, the throw escapes `candidate.edit`. The whole Arrange All then fails as a fault, where it should skip that one window. This is unlikely in practice.

**Fix:** Wrap the `applyDrop` in the same `do { … } catch { skipped += 1; continue }` as the `insertLeaf` branch.
