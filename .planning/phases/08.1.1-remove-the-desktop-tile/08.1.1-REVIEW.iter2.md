# Phase 08.1.1: Code Review Report

**Reviewed:** 2026-11-06T18:55:02Z
**Depth:** standard
**Files Reviewed:** 37
**Status:** issues_found

## Summary

I reviewed the 37 Sources files against `2aed288..HEAD`. The phase's three focus areas came out like this:

1. **layout.json legacy migration (trust boundary).** `LegacyNode` / `LayoutTree(legacyRoot:)` holds up against hostile input. Before the Desktop node is removed, the whole legacy shape goes through `validate()` with a stand-in panel. A Desktop node at any ID other than 0 is rejected, and so is a file that already uses the stand-in identity. A tree that is the Desktop alone ends with `root == nil`, which `validate()` accepts. `World.validate` still checks that node and group IDs are below `ids.next`. I found no way to inject or crash through it. The weak points are in what happens after decode:
   - the one-shot bring-back of windows a hidden Desktop had parked loses their home frames for windows not tracked at the moment of launch (WR-01);
   - there is no backup before this one-way, lossy schema bump (WR-04).
2. **Behaviour after removing the Desktop tile.** The phase handles `root == nil` everywhere it checks for it. It does not handle the related state where the tree has a root but no leaf is placed (every docked window minimized, hidden or full screen). The Desktop tile used to cover that case. Now New Windows: Tile, Dock Window (⌃⌥⌘D) and Arrange All all fail on what the user sees as an empty desk (CR-01). There are two smaller regressions:
   - the one-pass lost-room float no longer re-checks placeholders or leftover unfit windows (WR-02);
   - group-target hit testing over docked tiles relies on a z-order that does not exist under D-05 stacking (WR-03).
3. **Halves and thirds arithmetic.** `fourthShares` is correct for the new spans. The weights always sum to the stored total, `firstThird`/`lastThird` grow into an empty side, `middleThird` follows the D-14 "centred tile goes after" rule, and the grown labels match because `fourthSpan` returns the same `oneThird`/`twoThirds` constants that `FourthCopy` pattern-matches on. I found no defect there.

`necessity-review.md` was read. No necessity finding met the evidence rule. The remaining file-input guards (`ids.next >= 1`, the stand-in collision check) sit on a trust boundary.

## Critical Issues

### CR-01: A desk whose docked windows are all minimized or hidden can't take a new tile: New Windows: Tile, Dock Window and Arrange All all fail

**File:** `Sources/TransomEngine/Arranger+NewWindows.swift:34-41`, `Sources/TransomEngine/Arranger.swift:1373-1374`, `Sources/TransomEngine/Arranger+Commands.swift:150-157`

**Issue:** The phase replaced "dock beside the Desktop tile" with "on an empty tree, `.emptyLayout`", and the checks only test `tree.root == nil`. A tree can also have a root but no placed leaf. `resolve` gives no `nodeRects` when the root takes no part (`Resolve.swift:102`: `if try solver.aggregate(root) != nil { place }`). That happens when every docked window is minimized, hidden or full screen. Minimizing the only docked window is a common way to get there, and the user then sees an empty desk. Before this phase, the visible Desktop tile always took part and was always a target. Now:
- **autoTile:** `largestTile` returns nil and `root != nil`, so it hits `else { return [] }`. New Windows: Tile silently floats the window, which breaks D-08 ("with nothing docked: the window becomes the first tile").
- **dock():** `Planner.dockTarget` finds no leaf under the window's centre outside the 24 pt band and returns nil, so ⌃⌥⌘D (and the menu item, which stays enabled) only beeps.
- **arrangeAll():** `largestTile` is nil for every window, so every window is skipped, `skipped == order.count`, and the command beeps.

These are the core docking paths (CLAUDE.md "Core Value").

**Fix:** When the tree has a root but nothing is placed, dock at the layout edge. Inserting beside a root that takes no part gives the new leaf the whole visible frame, the same result `finderSplit` already gets through `.layoutEdge`:
```swift
// Arranger+NewWindows.swift
if let (target, rect) = tile ?? Self.largestTile(resolution, in: desk.tree) {
    drop = .tile(target, .edge(rect.width >= rect.height ? .right : .bottom))
} else {
    drop = desk.tree.root == nil ? .emptyLayout : .layoutEdge(.right)
}

// Arranger.swift dock()
let target = Planner.dockTarget(at: center, desk: desk, area: area, resolution: current.resolution)
    ?? (current.resolution.nodeRects.isEmpty ? .layoutEdge(.right) : nil)
guard let target else { return [.beep] }

// Arranger+Commands.swift arrangeAll(): treat "no placed leaf" like an empty tree
if trial.tree.root == nil {
    try trial.tree.applyDrop(.emptyLayout, leaf: node, states: states, ids: &trialIDs)
} else if let (target, rect) = Self.largestTile(resolution, in: trial.tree) { ... }
else { try trial.tree.applyDrop(.layoutEdge(.right), leaf: node, states: states, ids: &trialIDs) }
```
Add tests: one docked window minimized, then autoTile, dock and arrangeAll each dock the floater to fill the frame.

## Warnings

### WR-01: The one-shot `bringBackParked` drops home frames for parked windows it can't move at launch, leaving them off screen

**File:** `Sources/TransomEngine/Arranger.swift:856-870`, `Sources/TransomEngine/Arranger.swift:278-282`, `Sources/TransomEngine/Arranger.swift:772-775`

**Issue:** For a legacy file with a hidden Desktop, the floating frame the file stores can be the park rect. The old `reattach` called `recordFloatingFrame(info.frame)` on every present floater, so a relaunch while the Desktop was hidden saved the park rect, and this phase's `reattach` (line 774) still does the same. Only the home frame says where the window belongs. `bringBackParked` uses it once, during the launch inventory. At the end of that same `handle`, lines 278-282 clear `homeFrames` for every floater on every desk. A parked floater loses its home frame for good if any of these is true at that moment:
- it is not tracked yet (it is on a Space that isn't showing, which AX does not list, or its app's first AX answer is slow), or it is dormant;
- its desk's display is not connected: `displays.first(where: { $0.uuid == key.displayUUID })` fails and the loop does `continue`, where `rescueStranded` falls back to `?? displays.first`;
- `recordFloatingFrame` throws: the `try?` swallows the error and the loop moves on.

When such a window appears later, `planShown` moves it to the model's floating frame, which is the park rect. It stays off screen until the user runs Restore All. That contradicts D-02 ("windows parked by a hidden Desktop go back to their home frame") and the README promise ("windows a hidden Desktop tile had moved off screen come back").

**Fix:** Clear a floater's home frame only once it has been brought back. Either keep the WR-06 sweep away from home frames whose floating frame is stranded, or have the sweep skip windows not in `windows`. Fall back to `displays.first`, as `rescueStranded` does. Log a fault in place of `try?`. Run the same bring-back from the dormant-wake and `admit` paths for a stranded floater that has a home frame. Alternatively, fix it at migration time: in `LayoutStore`/`LayoutRestore`, when the file is schema 3 or older, write each floater's home frame into its stored floating frame, so the model frame is correct whenever the window shows up.

### WR-02: `planFloatingLostRoom` now runs once: a placeholder that becomes unfit after the relax throws `windowNotFound`, and the display stops being planned

**File:** `Sources/TransomEngine/Arranger.swift:2294-2320`

**Issue:** The old version looped until `plan.unfit` was empty and re-filtered waiting placeholders on every pass. The new one relaxes the placeholders in `plan.unfit` once (line 2301), plans again, then treats every remaining unfit window as a real window: `guard let frame = windows[window.identity]?.frame else { throw .windowNotFound(window) }`. A relaxed placeholder still takes part at 1x1 plus a gap, so it can push the victim choice onto a different placeholder. That placeholder isn't in `windows`, so the function throws. `planShown` then logs "could not plan" and skips the whole display on every replan until the placeholder resolves. Separately, the plan returned after the float (line 2320) is never re-checked. `tree.remove` → `normalize` can merge same-axis splits and clamp weights, which changes the floor/remainder rounding, so a window can be left docked with no frame and no notice.

**Fix:** Restore the loop and keep the "floating takes no room" simplification:
```swift
var plan = try Planner.plan(desk: desk, area: area, gap: gap, mins: mins)
var lost: [WindowRef] = []
while !plan.unfit.isEmpty {
    let waiting = plan.unfit.filter { isPlaceholder($0) && mins[$0] != nil }
    if !waiting.isEmpty { for w in waiting { mins[w] = nil }; plan = try Planner.plan(...); continue }
    // float plan.unfit (clamped into area), append to lost, re-plan
}
return (plan, lost)
```

### WR-03: The floating group target uses DesktopLayer insertion order as z-order, so a floater behind a docked window takes the drop

**File:** `Sources/TransomEngine/Arranger.swift:1748-1753`, `Sources/TransomEngine/Arranger+Tabs.swift:245-252`

**Issue:** The floating centre now beats the docked tile under it everywhere, not only on the Desktop tile (UI-SPEC discretion 3, RESEARCH A1: "a floater under the pointer is taken to be in front"). That assumption fails under D-05: plain macOS stacking means clicking a docked window brings it in front of floaters. `floatingGroupTarget` chooses its "topmost" floater with `layer.windows.reversed()`, which is the order windows were added to the layer, not the window server's stacking order. Nothing reorders that list on focus. So:
- hovering the middle of a docked window that hides a floater shows a Group preview, and dropping groups the dragged window with a window the user can't see;
- with overlapping floaters, the "topmost" one is effectively arbitrary.

**Fix:** Hit-test against real stacking. `CGWindowList.topmostWindow(at:)` already exists in `TransomMac`. Pass the CG window ID under the pointer into the hover (or into `DragSession` once per poll) and accept a floating group target only when that ID is the floater's own window, or the selected member of its group. Otherwise fall back to the docked tile's regions.

### WR-04: The schema 3 → 4 migration is one-way and lossy, and no backup is taken before the first save overwrites the file

**File:** `Sources/TransomMac/LayoutStore.swift:44-49`, `Sources/TransomMac/LayoutStore.swift:147-152`

**Issue:** Loading a schema 2 or 3 file migrates it in memory: the Desktop node, its weight and its hidden flag are dropped, and the World schema goes to 2. The next debounced save overwrites layout.json with schema 4. A downgraded Transom then sees `newerVersion`, disables saving and starts with no layout. The user's pre-upgrade arrangement is gone, and nothing on disk can bring it back. `LayoutStore.backUp(_:)` exists for exactly this (WR-04 of an earlier phase), but the migration path never calls it. `migrationLine` already detects the condition (`version != LayoutFile.schemaVersion`).

**Fix:** In `load()`, once a file older than the current schema decodes:
```swift
if version < LayoutFile.schemaVersion, !backUp("schema-\(version)") {
    Self.logger.error("could not back up the schema \(version) layout before migrating")
}
```
State in the README upgrade note that `layout.json.schema-3-<ts>` is the copy to restore after a downgrade.
