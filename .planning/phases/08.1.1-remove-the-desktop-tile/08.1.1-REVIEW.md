## Summary

This re-review covers the three fix commits for the previous round's findings: 58d6a44 (CR-01), 545888a (WR-01) and 71514f6 (WR-02). Since the last review, only `Arranger+Camera.swift`, `Arranger.swift`, `TreeEdits.swift` and `LayoutStore.swift` changed. I read each changed region with its callers. The rest of the scope is unchanged since the previous review, so its findings carry forward as written.

Claims were checked three ways:
- Reading the code.
- Running the three new regression tests (all pass).
- Running a throwaway fuzz of the new `LayoutTree.move(_:into:)`. The fuzz copied `TransomModel` into a scratch package, so no repo files changed.

**CR-01 is fixed.** `Arranger.exists(_:in:)` now returns false for `.spacer` as well as a missing node, using an exhaustive switch with no `default:`. Every place that resolves a view goes through it:
- `resolvedView`, for the committed view and its path fallback.
- `currentView`, which drops a pending target that is gone or now an empty area.
- `zoomTo` and `previewMove`.
- The back/forward `live` filters in `cameraStep` and `recordHistory`.

A view that lands on a spacer through `cameraSettle` (`:364`) is resolved again by `planShown` → `effectiveView`, so no `ViewPlanner.plan(view: .node(spacer))` call remains reachable. Other `ViewPlanner.plan` callers pass `.home` or `resolvedView`. Saved views store windows, not NodeIDs, so they are unaffected.

**WR-01 is fixed, and `move` holds up.** The new edit swaps the leaf's and the spacer's `nodes` entries. It leaves `states` alone, so a group's tab order, selection and member states survive. It then normalises and validates on a copy, so a throw leaves nothing behind.

The fuzz ran 4,000 random trees built from fourths, corners, vacates, removes and tab grouping:
- 11,864 random `move(leaf, into: spacer)` calls, 1,774 of them on tab groups.
- 0 throws and 0 invariant violations.
- States unchanged every time, and the leaf always ends up under the spacer's NodeID.
- Exact spans (E1, E4): the moved leaf's rect equalled the spacer's old rect, and every other window kept its rect, in all but one case. In that case, a layout of 1 pt tall tiles drifted by 6 pt when two spacers merged and a split collapsed. That is pixel rounding in the same class as IN-01, not a logic error.

Engine wiring:
- Undo: one step through `candidate.edit(key, history:)`.
- Cross-desk: a window or group from another desk takes the old `reflow` / `taken` path. On the target desk `state(of:)` is nil, and for a group `taken` is non-nil, so `move` is never reached for it.
- A torn tab and a floater still take remove-then-`fill`. That is safe: removing a tab never removes its leaf, and a floater is not in the tree.

**WR-02 is fixed.** `load()` now checks `backUp`'s result. A failed copy sets `savingDisabled`, the same session-long mechanism `.newerVersion` uses, so `layout.json` stays readable by an older build. `load()` is called once per launch (`ArrangeController.start`, `:219`), so a same-second name clash on the backup cannot happen within a session.

I found no new Critical or Warning issues. Six Info items remain: three carried forward and three new ones (IN-04 to IN-06) about test coverage and polish of the fixes.

## Info

### IN-01: Exact positions drift when a crowded side clamps to `minWeight` (carried forward)

**File:** `Sources/TransomModel/Fourths.swift:344-372` (clamping in `TreeEdits.swift` `normalize`)

**Issue:** `fitted` scales the tiles on a side down to fit their room. Tiles that land below `minWeight` (0.01) are later clamped up by `normalize`, and the window pays for the excess. The previous fuzz found 2 of 24,931 docks off by more than 4 pt. This round's `move` fuzz found the same class once: 6 pt in a layout with 1 pt tiles. E1 says "exactly".

**Fix:** Either reserve `minWeight` per tile on that side before scaling (and refuse with `splitFull` when the room cannot hold them), or document the limit in `insertFourth`'s doc comment.

### IN-02: An empty area's gap can make a window unfit, contrary to the doc (carried forward)

**File:** `Sources/TransomModel/Resolve.swift:131-139`

**Issue:** A spacer takes part with a zero minimum but still adds one `gap` to its split's aggregate. Take `[W | spacer]` with gap 8 in a 1440 pt area (inner 1424). W with a minimum width of 1420 is unfit, because 1420 + 8 > 1424, though alone it would fit.

**Fix:** Let a spacer whose share would fall below `gap` drop out of the aggregate, or document the one-gap cost.

### IN-03: New Windows: Tile and Arrange All prefer any empty area, however small (carried forward)

**File:** `Sources/TransomEngine/Arranger+NewWindows.swift:35-38`, `Sources/TransomEngine/Arranger+Commands.swift:153-155`

**Issue:** `largestEmptyArea` wins over the focused or largest tile whatever its size. A gap-handle drag can leave a `minWeight` sliver (about 14 pt on a 1440 pt display). A new window then fills that sliver and squeezes its neighbours, where before it would have split the focused tile.

**Fix:** Only use an empty area of at least `autoTileMinimum` (200×120). Otherwise fall back to the tile rule.

### IN-04: `LayoutTree.move(_:into:)` and the docked-group drag path have no direct tests

**File:** `Sources/TransomModel/TreeEdits.swift:160-173`, `Sources/TransomEngine/Arranger.swift:1866-1868`

**Issue:** The only test of the WR-01 fix is `ArrangerDragTests.aDockedWindowDraggedIntoTheEmptyAreaBesideItMovesThere`, which drags a single `.panel`. Nothing in `Tests/` calls `move` directly. The group branch (`taken == nil, !group.floating, let filled`) is not exercised. That branch moves a whole `.tabs` leaf and keeps its strip on the new NodeID. The scratch fuzz shows the model edit is sound for tab groups, but a regression there would go unnoticed.

**Fix:** Add a `TransomModelTests` case for `move`. Cover `[W | S]`, `[S1 | W | S2]`, a `.tabs` leaf, and the throws for a spacer `id` and a non-spacer target. Add a drag test that drags a docked two-tab group into the empty half beside it: expect `[.spacer, .tabs(...)]`, one undo step, and the group's strip rect equal to the half.

### IN-05: A pending zoom whose target becomes an empty area still commits it, then jumps

**File:** `Sources/TransomEngine/Arranger+Camera.swift:360-370`

**Issue:** `zoomTo` now refuses a spacer target, but a target can turn into one while its move is in flight. For example, the window is docked to a position mid-animation, and `vacate` leaves its NodeID as a spacer. `cameraSettle` still runs `commit(move.target, on:)` and pushes history for it. `planShown` → `effectiveView` then swaps in the path fallback with only an `.info("view node gone…")` note. The camera finishes animating to the empty area's rect, then the tiles jump to the ancestor view with no camera move. This is correct but jarring, and the history gets an entry for a view the user never saw settle.

**Fix:** In `cameraSettle`, check `Self.exists(move.target, in:)` first. If it fails, commit `resolvedView`'s fallback for the target's stored path, or re-issue `zoomTo` to that fallback so it animates. Skip `recordHistory` for a dead target.

### IN-06: `exists` now answers false for a node that exists

**File:** `Sources/TransomEngine/Arranger+Camera.swift:386-393`

**Issue:** After CR-01, `Arranger.exists(_:in:)` means "a valid view target". It returns false for a `.spacer` that is present in the tree. It also serves the history `live` filters in `Navigator.swift:246` and `recordHistory`. A future caller that reads the name literally, for example to check that a NodeID is still in the tree before a model edit, would wrongly treat an empty area as gone.

**Fix:** Rename it to `isViewable(_:in:)` (or `isLiveView`). The doc comment already says "An empty area is never a view".
