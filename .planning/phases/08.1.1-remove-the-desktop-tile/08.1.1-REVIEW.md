## Summary

This round adds the `Node.spacer` empty-area leaf, layout.json schema 5, exact docking positions, corner quarters, and a group dwell ranked by the window server's stacking. I checked the code against 08.1.1-CONTEXT.md D-16..D-20 and rules E1-E7 in 08.1.1-20-PLAN.md. Claims were checked two ways: by reading the code, and by running a throwaway probe. The probe copied `TransomModel` and `TransomEngine` into a scratch SwiftPM package, so no repo files changed.

**What holds up:**
- **Schema-5 load path (trust boundary).** `validate()` rejects a spacer root, adjacent spacers, and any split with no window under it. The windowless-split check is correct: the deepest windowless split must hold two or more children, every one a spacer. The validation stays iterative. The version probe still refuses newer files (`.newerVersion`), and older files are backed up before the first schema-5 save. The Desktop bring-back and the migration log line are now gated on `version <= 3`.
- **Tree arithmetic.** I fuzzed `insertFourth`, `insertCorner`, `vacate`, `removeLeaf`, `fill` and minimise toggles: 3,000 random runs, 24,931 dock checks, gap 0. It found no invariant violation, no thrown error, and no overlapping windows. Only 2 docks missed their exact span (IN-01). `normalize` always terminates, and a desk holding only spacers becomes an empty desk.
- **Event tap.** The stacking read is one `CGWindowListCopyWindowInfo` per mouse-down on a tracked window or tab. It runs in `ArrangeController.handle` on the main actor, not in the tap callback, and does no AX work. Drag events never trigger it.
- **Exhaustive switches.** Every `Node` switch handles `.spacer` explicitly, with no `default:` arm.

**What fails:**
- **CR-01 (zoom state).** A view on a node that becomes an empty area stops all arranging on that display, and the user cannot zoom out.
- **WR-01.** Dragging a docked window into the empty area next to it, the drag rule E6 describes, silently snaps back in the most common layout.
- **WR-02.** The one-way schema upgrade still goes ahead when its backup fails.

## Critical Issues

### CR-01: A view on a node that becomes an empty area stops arranging that display and blocks zooming out

**File:** `Sources/TransomEngine/Arranger+Camera.swift:97-101` (also `:245`, `:385-388`; `Sources/TransomEngine/ViewPlanner.swift:12-25,55`; `Sources/TransomModel/TreeEdits.swift:133-145`; `Sources/TransomEngine/Arranger.swift:2161-2184`)

**Issue:** `vacate` (E4) changes a window leaf into `.spacer` and keeps its NodeID. `fill` does the reverse, so an Undo after a fill also changes a window leaf back into a spacer under the same ID. Code that resolves a view only checks that the node exists:

```swift
if tree.node(id) != nil { return .node(id) }   // resolvedView: a spacer passes
```

`ViewPlanner.plan(view: .node(spacer))` then calls `subtree(at:)`, which builds `LayoutTree(root: spacer, …)`. Validation then throws `invariantViolated("root nN is an empty area")`.

The probe confirmed both steps:
- Start from `vertical[(A | B) / C]`, run `vacate(A)`, then `insertFourth(firstHalf, .horizontal)`. Node `A` survives as `.spacer`.
- `ViewPlanner.plan(desk:view:.node(A)…)` then throws that error.

How a user reaches this with zoom on: zoom into tile A (step in or frame window), then press ⌃⌥⌘ "Dock to Left Half" on A. A docked-group drag with ⌃ does the same. So does tiling a new window into an empty area, zooming onto it, then choosing Undo Layout Change. After that:
- `planShown` takes the `catch { faults.append(...); continue }` branch on every replan. That display gets no frames, no tiling, no strips and no gap handles. This breaks the Core Value: tiling must keep working.
- `widen(toShow:)`, and every later `zoomTo`, fail in `planTiles(from: current)`, because the *current* view is the spacer. The user cannot zoom out. Only turning zoom off or Restore All Windows (`goHome`) recovers.
- The same happens if a pending move's target becomes a spacer before it settles: `commit(move.target)` at `:363`.

**Fix:** Treat an empty area as a gone view node everywhere a view is resolved:

```swift
// Arranger+Camera.swift
private static func isViewNode(_ id: NodeID, in tree: LayoutTree) -> Bool {
    switch tree.node(id) { case .spacer?, nil: false; default: true }
}
func resolvedView(for key: DeskKey) -> ViewTarget {
    guard camera.enabled, case .node(let id)? = camera.views[key], let tree = world[key]?.tree else { return .home }
    if Self.isViewNode(id, in: tree) { return .node(id) }
    return camera.paths[key]?.last { Self.isViewNode($0, in: tree) }.map { Navigator.target($0, in: tree) } ?? .home
}
// zoomTo (:245) and exists (:385): refuse / return false for a spacer the same way.
```

Optionally, give `ViewPlanner.plan` a parent fallback as defence in depth. Add an engine test: zoom into a leaf, dock it to Left Half so that its spacer survives, then assert that `planShown` emits no fault and the view falls back.

## Warnings

### WR-01: Dragging a docked window into the empty area beside it is a silent snap-back

**File:** `Sources/TransomEngine/Arranger.swift:1857-1883` (with `Sources/TransomModel/TreeEdits.swift:117-121,338,363-369`; catch at `Arranger.swift:1830`)

**Issue:** For a drag, `DropZones` returns `.fill(S)` from the 24 pt edge band, using the tree that still holds the dragged window. `dropping` does not vacate for `.fill`. It calls `desk.tree.remove(window)` first, and then `applyDrop(.fill(S))`. The removal applies E5:
- It gives the window's share to the spacer beside it.
- `normalize` then merges adjacent spacers, keeping the *first* one, and collapses a tree that holds only spacers to an empty desk.

So when `fill(S)` runs, `S` is often gone and it throws `nodeNotFound(S)`. `decide` catches the error and returns `miss`, so the window snaps back. The probe shows:
- `[W | S]`, the layout every lone half-dock produces: `remove(W)` empties the tree, and `fill(S)` throws `nodeNotFound(n2)`.
- `[S1 | W | S2]` with S2 as the target: S1 absorbs W's share and merges with S2, so the fill throws.
- When it does work (`[A .25 | W .25 | S .5]`), W lands at 0.75 instead of the 0.5 empty area. Its old share flowed into S first. This contradicts E1 and E3.

This defeats E6's "previews that empty area and docks into it" in the most common case: move a lone Left Half window to the right half by dragging to the right edge.

**Fix:** When `.fill(s)` targets the same desk the docked leaf is on, move the leaf in one edit instead of remove-then-fill. For example, add a model edit:

```swift
/// E4 + E6: the docked leaf `id` takes the empty area `spacer`'s place; its old place becomes an empty area.
public mutating func move(_ id: NodeID, into spacer: NodeID) throws(LayoutError) {
    guard nodes[spacer] == .spacer, let leaf = nodes[id], Self.members(of: leaf) != nil else { throw .notALeaf(id) }
    var next = self
    next.nodes[spacer] = leaf
    next.nodes[id] = .spacer
    next.normalize(); try next.validate(); self = next
}
```

Use it in `dropping` for both the single-window path and the docked-group path. Add drag tests for `[W | S]` and `[S1 | W | S2]`.

### WR-02: The one-way schema 4→5 upgrade goes ahead when the pre-migration backup fails

**File:** `Sources/TransomMac/LayoutStore.swift:50-54` (and `backUp` at `:111-121`)

**Issue:** D-20 asks for a backup before migrating. An older (schema-4) build refuses a schema-5 file as `.newerVersion`, so the backup is the only copy a downgrade can use. But `backUp`'s `false` result is ignored and only logged inside `backUp`. The next `save` overwrites `layout.json` with schema 5 anyway. If the copy fails (disk full, permissions, a name clash in the same second), downgrading loses every saved layout and view. The `version <= 3` paths have the same gap. CLAUDE.md's "Silent Fallbacks" rule applies.

**Fix:** Keep the file untouched when the backup fails:

```swift
if version != LayoutFile.schemaVersion, !backUp("schema-\(version)") {
    savingDisabled = true
    Self.logger.error("could not back up a schema \(version) layout.json; not saving layouts this session so it stays readable")
}
```

Alternatively, retry the backup at the first `save` and refuse that save if it still fails.

## Info

### IN-01: Exact positions drift when a crowded side clamps to `minWeight`

**File:** `Sources/TransomModel/Fourths.swift:344-372` (clamping in `TreeEdits.swift` `normalize`)

**Issue:** `fitted` scales the tiles on a side down to fit their room. Tiles that land below `minWeight` (0.01) are later clamped up by `normalize`, and the window pays for the excess. The fuzz found 2 of 24,931 docks off by more than 4 pt. In one, a corner meant to be 600 pt wide came out 590 pt, next to a row of nine children with several at 0.01. E1 says "exactly".

**Fix:** Either reserve `minWeight` per tile on that side before scaling (and refuse with `splitFull` when the room cannot hold them), or document the limit in `insertFourth`'s doc comment.

### IN-02: An empty area's gap can make a window unfit, contrary to the doc

**File:** `Sources/TransomModel/Resolve.swift:131-139`

**Issue:** A spacer takes part with a zero minimum but still adds one `gap` to its split's aggregate. Take `[W | spacer]` with gap 8 in a 1440 pt area (inner 1424). W with a minimum width of 1420 is unfit, because 1420 + 8 > 1424. Alone it would fit. The plan's statement that a spacer never makes a window unfit holds only when the minimum leaves at least one gap of slack.

**Fix:** Let a spacer whose share would fall below `gap` drop out of the aggregate. One way: return nil when the other taking-part children already fill the split. The simpler option is to document the one-gap cost.

### IN-03: New Windows: Tile and Arrange All prefer any empty area, however small

**File:** `Sources/TransomEngine/Arranger+NewWindows.swift:35-38`, `Sources/TransomEngine/Arranger+Commands.swift:153-155`

**Issue:** `largestEmptyArea` wins over the focused or largest tile whatever its size. A gap-handle drag can leave a `minWeight` sliver (about 14 pt on a 1440 pt display, which `resolve` floors further). A new window then fills that sliver. Water-filling pins it at its minimum and squeezes the neighbours, where before it would have split the focused tile. This follows plan 22 as written, but the result can surprise users.

**Fix:** Only use an empty area of at least `autoTileMinimum` (200×120). Otherwise fall back to today's tile rule.
