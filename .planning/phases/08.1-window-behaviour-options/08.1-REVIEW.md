## Warnings

### WR-01: `autoTile` runs during a live drag, and a resize or gap drag then commits a wrong boundary

**File:** `Sources/TransomEngine/Arranger+NewWindows.swift:17-24`, with `Sources/TransomEngine/Arranger.swift:2067-2086` (`edgeMoves`) and `Sources/TransomEngine/Arranger.swift:2188` (live gap)

**Issue:** The guard checks for a pause and for settling, but not for `drag` or `liveGap`. Before this phase a window opening mid-drag only joined the Desktop layer, so the tree never changed under a drag. In Tile mode it does.

**Failure scenarios:**
1. **Edge resize.** The user is dragging docked window A's edge, so A is the most recently focused. Another app opens window N, and D-02 splits A's tile. `dragPlans` is cleared (`Arranger.swift:285`), so `edgeMoves` compares A's real, unwritten frame against its new half-size tile. It reads that as a large boundary move. `followResize` applies it live, and mouse-up commits it with an undo step. A keeps its old width and N ends up at its minimum, or at about 1% of the split if no minimum is known yet.
2. **Gap drag.** `BoundaryMove(live.handle, live.delta)` holds a child index. If N docks into the same split at or before that index, the index is off by one and a different boundary moves.
3. **Move drag.** The preview on screen and `session.current` stay from the old plan until the hover changes, because a world change doesn't clear `session.decision`. The drop lands somewhere other than the preview shows, which breaks the WYSIWYG rule in the comment at `Arranger.swift:1918`.

**Coverage:** no test; 08.1-06-SUMMARY says so.

**Fix:** Float the window for the rest of this gesture, as the paused case does. `liveGap` is `private` (`Arranger.swift:221`), so it needs a wider access level.
```swift
guard newWindows == .tile, drag == nil, liveGap == nil, pauseReasons.isEmpty, !sessionPaused, !settling,
```

### WR-02: Undoing an auto-tile on a hidden Desktop floats the window at its current frame, which can be off screen

**File:** `Sources/TransomEngine/Arranger.swift:1453-1457` (the `admit` loop in `undo`), `Sources/TransomEngine/Arranger.swift:1291-1292` (`admit`), `Sources/TransomEngine/Arranger+NewWindows.swift:36-38`

**Issue:** With a hidden Desktop the undo snapshot doesn't hold the window, so `undo` re-admits it using `windows[id].frame`. That is where the window is now, not where it opened. `admit` also overwrites the correct `wantedFrames` entry that `autoTile` recorded on line 52.

**Failure scenario:**
1. Zoom is on and the Desktop is hidden. New window N auto-tiles, doesn't fit and collapses, so it is parked at `DisplayInfo.parkedFrame`, with only a 1 pt corner on the display. N is also parked if the camera has since zoomed elsewhere.
2. The user presses Undo. `admit` adds N as floating at the parked frame and records that as its wanted frame.
3. `Planner` only clamps a floater that overlaps a tile, so N normally stays parked. The exception is a tile covering the display's last point.
4. `rescueStranded` runs only at launch, on Restore All and when zoom is turned off while paused. N stays off screen with no visible way back until the user chooses Restore All Windows.

Even without parking, N floats at its old tile frame rather than where it opened, unlike the case with the Desktop shown (`itIsOneUndoStepAndUndoFloatsItWhereItOpened`).

**Coverage:** `docksWithoutShowingAHiddenDesktopAndUndoShowsIt` only checks that a floating frame exists.

**Fix:** Have `admit` prefer the frame already recorded for a window on no desk.
```swift
let frame = wantedFrames[info.window.identity] ?? info.frame
try world.reflow(key) { desk, _ throws(LayoutError) in try desk.desktop.add(info.window, frame: frame) }
wantedFrames[info.window.identity] = frame
```
Check first that `forget` always clears `wantedFrames` (it does at `Arranger.swift:1156`, except for the hold-for-quit path), so an old frame can't return for a reused identity.

### WR-03: The first new window after launch ignores the focused tile (D-02)

**File:** `Sources/TransomEngine/Arranger+NewWindows.swift:31`, with `Sources/TransomEngine/Arranger.swift:1042-1044`

**Issue:** `focusOrder` is only fed by `.windowFocused`, which fires on a change. A window that already had focus when Transom launched is not in it.

**Failure scenario:** Transom relaunches and restores a layout with Terminal docked and focused. The user presses ⌘N in Terminal. `focusOrder` holds only the new window, so `focused` is nil and the window splits the largest tile, usually the Desktop, instead of landing beside Terminal. This was seen in the VM (`deferred-items.md`), and `OptionsBundleIntegrationTests` pins neither way. The result is valid but wrong against D-02.

There is a related gap in the same line. `focusOrder.first` means most recently focused, not focused now. If the user activates an app with no tracked window, such as Finder with only the desktop, no event arrives. The next new window then goes beside the old tile rather than following D-03.

**Fix:** Once the first complete sweep ends, emit one `.windowFocused` for the frontmost app's window. `AXWindowSystem.focusedWindow(of:)` already resolves it, and `ArrangeController.commandContext` already uses that route. Swap and view navigation read the same list, and they only gain from an accurate first entry.

### WR-04: The ⌥ strip stays on after a lost mouse-up until the next normal press

**File:** `Sources/TransomMac/Input/InputTap.swift:155-158`, `:163` and `:199`; `Sources/TransomEngine/Arranger.swift:212-215` and `:1033`; `Sources/TransomMac/ArrangeController.swift:337-344`

**Issue:** The strip is derived from `drag?.kind == .move`, and only the next press clears a stale session. So it stays on in three cases where the mouse-up is never seen:
- **Tap disabled.** `.tapDisabledByTimeout` or `.tapDisabledByUserInput` during a drag re-enables the tap and tells nobody.
- **Tap stopped.** `stopTap` leaves `arranger.drag` in place, and the `dragOption` lock lives on `InputTap`, not `TapBox`, so a restarted tap keeps `.always`.
- **Session switch.** `.sessionPaused(true)` only sets a flag.

**Failure scenario:** The tap times out mid-drag and the mouse-up is lost. From then on every `flagsChanged` has ⌥ removed. RESEARCH measured that this makes `combinedSessionState` read no ⌥, so apps that read it, or that follow `flagsChanged`, don't see ⌥ while it is held. A keyboard-only user can stay like this indefinitely.

A consumed press doesn't fix it either. The callback clears the lock on a zoom or green-button press, but the Arranger never sees that press, its `drag` is still `.move`, and the next Arranger change publishes `.always` again (`ArrangeController.swift:34`). The comment at `ArrangeController.swift:434-436` covers the opposite race only.

The harm is limited: `keyDown` isn't in the mask, so typed ⌥ characters are unaffected, and the next normal press clears it.

**Coverage:** `aMoveSessionAfterALostMouseUpAsksForTheStripAgain` covers recovery at the next press, not the gap before it.

**Fix:** Don't strip a `flagsChanged` when the left button is up, which needs no message from the main thread. Add a parameter to `DragOptionRule.strips`, so it stays pure:
```swift
let held = type != .flagsChanged || CGEventSource.buttonState(.hidSystemState, button: .left)
if held, DragOptionRule.strips(type: type, flags: event.flags, state: box.dragOption.withLock { $0 }) { ... }
```
Check the cost of `buttonState` against the tap's 1 ms budget. It runs only on `flagsChanged` while a session is live if the state is read first. Also end the session on `.sessionPaused(true)`.

### WR-05: A new window whose minimum isn't known yet can float with a notice, against D-06

**File:** `Sources/TransomEngine/Arranger+NewWindows.swift:46-49`, with `Sources/TransomEngine/Arranger.swift:2234-2235` and `:2328`

**Issue:** The fit check only knows minimums already learned. The first window of an app with a large minimum passes it and docks. The app then refuses the size, the learner confirms that about a second later, and `planFloatingLostRoom` floats the window with `.notice(.lostRoom)`.

**Failure scenario:** Tile mode, a 500 pt focused tile, and the first Slack window of the session with an 800 pt minimum. The window docks, overflows its tile for about a second, then floats with a lost-room toast. UI-SPEC says "No beep, notice or announcement, because nothing the user did was refused". With zoom on the same path runs first (`Arranger.swift:2230`), so it floats with a notice rather than collapsing as D-06 says. The undo step stays, and undoing it changes nothing visible.

**Coverage:** `noRoomWithZoomOffFloatsSilently` passes because its fixture gives the window a minimum before it arrives. Later windows of the same bundle are protected by `bundleHints`, so this is a first-window problem.

**Fix:** Record auto-tiled windows in a session set until their first read-back or learned minimum. If a lost-room float is only those windows, leave them out of the notice. With zoom on, add them to `camera.collapsible` so they collapse instead. Otherwise amend D-06 and the UI-SPEC to say this case shows the notice.

### WR-06: Fourth guides disappear for the rest of the drag after a panel rebuild

**File:** `Sources/TransomMac/Overlay/PreviewPanel.swift:181-186`, `:229` and `:352-373`; `Sources/TransomEngine/Arranger.swift:1700`

**Issue:** `rebuildPanels` clears `fourthGuides`, but the Arranger's `session.guides` stays non-empty. `settleDrag` only sends guides when that list is empty, and `followGuides` only when the bands change.

**Failure scenario:** During a ⌃-drag a display changes, or `leftOnAnotherSpace` triggers a rebuild inside `overlay(_:)` when the next result preview is shown. The guides vanish until ⌘ flips the axis or ⌃ is pressed again. UI-SPEC says they last "until ⌃ is released or the drag ends". The result preview recovers on the next hover change. This is a documented known limit and nothing stays on screen, but it does break the spec.

**Fix:** Keep the guides across the rebuild, with no engine change. Save `fourthGuides.mapValues(\.rects)` before the wipe. After the panels exist, re-apply each non-empty entry for a display that still exists, ordering its panel front.

### WR-07: A fourth with nothing else taking part stores about 1% weight, so the window collapses when the others return

**File:** `Sources/TransomModel/Fourths.swift:84` and `:110`

**Issue:** When `room` is 0, the new window's share is `max((end - start) * 0, minWeight)`, or 0.01 of the split. That is fine while nothing else shows, and `withNothingElseTakingPartTheWindowFillsTheDesk` checks only that.

**Failure scenario:** Desktop hidden, one docked window X. The user presses ⇧⌃⌥⌘1 on X, and it fills the desk. The user then chooses Show Desktop Tile. X now has 1% of the width against the Desktop's 99%: a write of about 14 pt on a 1440 pt display until the app refuses and the learner raises it to its minimum. The same happens when a minimized sibling returns.

**Fix:** Give the window its real share of the stored total when `room` is 0.
```swift
let basis = room > 0 ? room : weights.reduce(0, +)
shares.insert(max((end - start) * basis, minWeight), at: index)
```
With `room == 0` the window spans 0 to 1, which gives it half the split on return, and it still fills the desk while it is the only one taking part. Use `slot.span`'s width instead if a ¼ share on return is preferred; D-14 doesn't decide this.

### WR-08: Dragging a docked window onto the zone it already holds adds an undo step

**File:** `Sources/TransomEngine/Arranger.swift:1966-1982` (`commitDock`), compared with `Sources/TransomEngine/Arranger+Commands.swift:45-48`

**Issue:** `dockFourth` has a no-change guard because `commit` can't tell: the new leaf has a new ID. `commitDock` has no such guard. UI-SPEC says the release "leaves it there, nothing refused".

**Failure scenario:** The user ⌃-drags a docked window and releases it on its own zone. The tree gets a new leaf and the history a new step, and "Docked to 1st column" is announced. The next Undo appears to do nothing. Repeats can push older steps out of the 50-step history (`Undo.swift:8`).

**Fix:** Apply the same comparison in `commitDock` for `.fourth` targets, and skip the commit when frames are unchanged and the window was already docked. Pull it into one helper used by both paths.

### WR-09: The rate limit is per command, so the ten new URLs allow ten layout edits a second

**File:** `Sources/TransomEngine/TransomURL.swift:20-25` and `:95-105`, `Sources/TransomMac/CommandGate.swift:22`

**Issue:** `TransomURL.swift` says anything from any app or web page can open these URLs. `lastAdmitted` is keyed by `Command`, so `dock-column-1`, `dock-column-2` and the rest each get their own second. Before this phase the layout-editing URLs were few (`toggle-desktop`, `restore`, `split-finder` and the tab commands).

**Failure scenario:** A page the user has allowed to open `transom://` links cycles through the ten dock URLs on a timer. The focused window is rewritten about ten times a second, each change is saved, and each adds an undo step. The 50-step history is gone in about five seconds, so the user can't undo back to their layout. No data leaves the machine and it stops when the page closes, but this is the input the limiter exists to contain.

**Fix:** Give the dock family one key.
```swift
let key: Command = if case .dockFourth = command { .dockFourth(.first, .horizontal) } else { command }
```
This changes UI-SPEC Surface 4's "a second call inside 1 s" row for scripts that dock several windows quickly, and the CLI shares this gate. If that matters, allow a small burst, or apply the family key only to the URL route.

### WR-10: `vm-session.sh` checks the VM lock but never holds it, and it stops a running VM

**File:** `scripts/vm-session.sh:17` and `:19-21`

**Issue:** Line 17 only tests that the lock exists, because the child script needs to take it with `mkdir`. The VM is then unprotected through boot, up to 10 minutes, and again after the child exits. Line 19 stops the VM unconditionally, although the header says it starts a *stopped* VM, and the `EXIT` trap stops it again.

**Failure scenarios:**
- `vm-cli-check.sh` or a UAT re-check starts while a session is booting. It takes the lock, then the session runs `pkill -9 -x 'Transom Debug'` in the guest and fails to get the lock itself, so its exit trap stops the VM under the other run.
- Two sessions start together. Each stops the other's VM.
- A VM someone is using by hand without the lock is stopped with no warning, losing whatever the guest hasn't written out.

All of this happens inside the test VM, never on the host.

**Fix:** Take the lock in `vm-session.sh` and hand it to the child through an environment variable that the three lock-taking scripts honour. Refuse to run if the VM is already up.
```bash
mkdir .build/transom-vm.lock 2>/dev/null || { echo "vm-session: VM busy" >&2; exit 1; }
trap 'rmdir .build/transom-vm.lock' EXIT
# Before any trap stops the VM, so a refusal leaves a running VM alone.
if tart ip "$vm" >/dev/null 2>&1; then echo "vm-session: $vm is already running" >&2; exit 1; fi
trap 'tart stop "$vm" >/dev/null 2>&1 || true; rmdir .build/transom-vm.lock' EXIT
export TRANSOM_VM_LOCK_HELD=1   # vm-live-test.sh, vm-cli-check.sh and vm-spike.sh skip their mkdir and rmdir when set
```

### IN-02: A new window on a Space that isn't showing always floats

### IN-04: The strip starts late when ⌥ is already down at the press

**File:** `Sources/TransomEngine/Arranger.swift:212-215`

This is accepted, but holding ⌥ first is the natural way to read "Hold ⌥", and host UAT item D3 covers only ⌥ pressed mid-drag.

### IN-05: Smaller script gaps

**File:** `scripts/vm-live-test.sh:18`, `scripts/vm-cli-check.sh:16`, `scripts/vm-session.sh:20`, `:33` and `:37`, `scripts/vm-bundle-check.sh:9-11`, `scripts/vm-quit-check.sh:9-11`, `scripts/vm-live-test.sh:34`

**Issue:**
- **Empty IP.** `vm-session.sh` guards it because `tart ip` can return nothing after sleep, but `vm-live-test.sh` and `vm-cli-check.sh` build `admin@` from it and only fail later, confusingly, at `rsync` or `ssh`.
- **Boot failure.** A `tart run` that dies at once isn't noticed. The loop keeps polling, and with `ConnectTimeout=5` plus `sleep 5` it can last 10 minutes while the message says 5.
- **App path argument.** Both wrapper scripts `cd "$root"` before reading it, so a relative path resolves against the repo rather than the caller's directory. A trailing slash makes `cp -R` copy the bundle's contents instead of the bundle.
- **Stale comment.** `vm-live-test.sh:33` names only `vm-quit-check.sh`.

**Fix:** Add `[ -n "$ip" ]` to the two scripts, `kill -0 $!` in the loop, and resolve the path before the `cd`.

### IN-06: Impossible-state guards in `autoTile` and `insertFourth`

**File:** `Sources/TransomEngine/Arranger+NewWindows.swift:28`, `Sources/TransomModel/Fourths.swift:62`
**Category:** necessity

**Issue:** Subtype: impossible-state guard. Line 28 can't fail, because line 27 has just added the desk if it was missing. `Fourths.swift:62` can't fail either: `insertLeaf` either keeps a root that exists or sets a new one (`TreeEdits.swift:56-71`), and the nil-root case returned at line 49 of `Fourths.swift`. The first also turns a broken invariant into a silent float, which `CLAUDE.md`'s Silent Fallbacks rule warns against.

**Fix:** A human decides whether to remove them. If kept, the line 28 guard should report a fault rather than return `[]`.
