## Eliminated

- hypothesis: The Hold ⌥ / ⌥-modifier path skips the floater check.
  evidence: The engine test with `.dragToDock(.holdOption)` and [.option] groups when T's focus is recorded. hover() reaches floatingGroupTarget for every display target (Arranger.swift:1752).
- hypothesis: The floater check doesn't run when the dragged window is floating, or the docked region preempts it.
  evidence: For a floating W, `beneath` is B's leaf (Arranger.swift:1751). The floater check runs before the tile switch and nils `target` when it hits (1752-1757). The repro groups when focus is right.
- hypothesis: T's centre hit area is computed wrongly.
  evidence: It uses the middle 50% of windows[T].frame (Arranger+Tabs.swift:264-266), the same frame used for containment. The repro with T's centre groups.
- hypothesis: ⌥-press on W (another app) hid FileZilla, so T was not present.
  evidence: runningboard showed FileZilla "visiblity is yes" from 14:29:04.266 to 14:29:14.949, until Warp came front, so it was not hidden. lsappinfo shows Hidden=false.
- hypothesis: T was minimized or absent during 7a (layout.json now says FileZilla is absent).

## Resolution

root_cause: Two conditions combine (the AND-gate). First, Arranger+Tabs.swift:262 (`floatingGroupTarget`) decides whether a floater is in front of the docked tile beneath it from `focusOrder` alone, and treats a floater whose focus was never recorded (`.max`) as behind. Second, on the host the shell's lossy, asynchronous focus feed left B (Safari) ahead of T (FileZilla). The function returns nil, so `hover` (Arranger.swift:1752) keeps `.tile(B, .top)`. That gives B's Top half preview, and the release docks W.
why_tests_missed: ArrangerTabsTests.swift:733 `aFrontFloatersCentreGroupsAheadOfTheDockedTileBeneath` sends no windowFocused, so both recencies are .max and the floater wins by default. No test records the docked window's focus without a later floater focus, which is the host's normal state, since B was focused to press ⌃⌥⌘D. `aFloaterBehindAFocusedDockedWindowDoesNotGroup` (:753) assumes focusOrder is truthful. FakeWindowSystem emits windowFocused only for `.focus` commands, never for user clicks or activations, so no engine or live test ties focusOrder to real stacking. The 7a scenario had no VM live test; it was human-only (VERIFICATION item 7).
fix_direction: Rank by real stacking instead of focus recency. In TransomMac, at drag start (or on each hover change), read `CGWindowList.onScreenFrontToBack()` (CGWindowList.swift:16). This is one window-server read, with no AX. Pass the front-to-back order of tracked windows into the session as an engine input. In floatingGroupTarget, pick the frontmost of {floaters containing the point, the docked window beneath}, excluding the dragged window. Keep focusOrder only as the headless fallback. Partial stopgap, not sufficient alone: do not let the tile win when the floater's recency is .max. That fixes "never recorded" but not "B recorded later". Regression tests: an engine test with B focused, T unfocused or older, and a z-order input placing T in front (red today), plus the 7a scenario as a VM live test with three different apps.
